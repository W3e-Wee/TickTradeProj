## Stage A

Stage A consumes one trade at a time through the supplied reader and maintains VWAP, one-second OHLC bars and moving-average crossover signals. A bar is flushed at end of input, and crossover classification uses exact scaled-integer sums so all implementations share the same signal sequence.

## Stage B

Stage B measures increasingly efficient data and indicator representations while preserving the shared result contract. The measured ladder is:

| Version | Implementation |
| --- | --- |
| v0 | `sscanf`, double values, naive SMA, streaming, `-O0` baseline |
| v1 | Same engine at `-O2` |
| v2 | Same engine at `-O3` |
| v3 | Same baseline at `-O2`, with `-mcpu=cortex-a76` when `PI=1` |
| v4 | Manual parser |
| v5 | Running-sum SMA |
| v6 | Scaled integer values and exact crossover comparison |
| v7 | Static in-memory trade array bounded by `MAX_TRADES` |
| v8 | Exact-sized allocated in-memory trade array |
| v9_soa | SoA stretch engine with exact scaled crossover comparison |

The end-to-end time includes the engine's input and allocation work; process time measures the strategy loop. `make bench` discards a warm-up before collecting configured repeats.

- Commands: [Stage B command sequence](MAKE_COMMANDS.md#stage-b)
- Files: [Stage B source map](FILES_BY_STAGE.md#stage-b)
- Results: [Stage B output paths](RESULTS_LOCATIONS.md#stage-b)

## Stage C

Stage C schedules each trade from its market timestamp and chosen replay speed, then records engine results and timing samples without rendering on the decision path. Processing time is the engine-step duration; latency is decision time minus scheduled release time; lag is the nonnegative latency, and the CSV reports the maximum lag and the fraction of decisions processed after release.

- Commands: [Stage C replay, latency and assembly commands](MAKE_COMMANDS.md#stage-c)
- Files: [Stage C source map](FILES_BY_STAGE.md#stage-c)
- Results: [Stage C output paths](RESULTS_LOCATIONS.md#stage-c)

## Rival bot demonstration

The rival starts flat and buys only when flat or sells only while holding. A response strictly faster than the reaction threshold fills at the signal trade; equal or slower response fills at the next trade, and an unfilled last-trade signal is discarded.

The sweep compares P&L against the fastest core at each reaction time. Find where the baseline `money_lost` becomes positive to see the tested region where the slower implementation gives up value; an open position is not marked to market at end of file.

- Commands: [Rival demonstration](MAKE_COMMANDS.md#rival-bot-demonstration)
- Files: [Rival source map](FILES_BY_STAGE.md#rival-bot-demonstration)
- Results: [Rival output paths](RESULTS_LOCATIONS.md#rival-bot-demonstration)

## Stretch goals

The stretch programs isolate optional optimizations from the normal C build. The current NEON kernel uses compiler intrinsics with a portable scalar C `-O3` comparison; this Windows session does not verify AArch64 code generation.

### NEON kernel

The NEON program sums price-quantity products and compares the intrinsic kernel with the optimized scalar reference. The source is intrinsic-based rather than a hand-written `.S` file.

Replay allocates latency samples before processing begins, sorts them after the loop and reports p50/p99 using nearest-rank sample positions. This keeps allocation and sorting outside the engine decision step.

## Codebase map

- `provided/`: untouched course timing, LED and trade reader helpers.
- `src/common/`: platform boundary, indicators, exact arithmetic, replay, latency, rival and result modules.
- `src/stage0/`, `src/stageA/`, `src/stageA_plus/`, `src/ladder/`, `src/stageC/`: course stages and engine variants.
- `src/stretch/`: NEON intrinsics, SoA and the two Python implementations.
- `src/tools/`, `tests/`, `scripts/`, `config/`: support programs, checks, plots and build configuration.

## Developer rules

Keep operating-system APIs inside `src/common/platform.c` and its public header. Keep provided files unchanged, preserve exact scaled-integer crossover decisions, write result files outside timed and replay decision regions, and update the four audit documents when Make targets, files, external tools or output paths change.
